# BrowserCrew Organization Map

| Repository | Canonical responsibility |
|---|---|
| browsercrew | Product, runtime, browser harness, architecture, roadmap |
| Progress-Memory | Current state, routing, blockers, handoffs |
| Workflows | Demonstrated and designed procedures |
| Skills- | Reusable versioned capability contracts |
| Agent-Registry | Agent roles and teams |
| Automation | Scheduled/triggered orchestration and operational automation |
| design-system | Product UI/UX system |
| Brand | Identity, positioning, voice, messaging |
| Website | Commercial website implementation |
| Docs- | Public documentation |
| Marketing | GTM, acquisition, campaigns, growth |
| Content | Content production library |
| Competitor-Analysis | Competitive intelligence |
| AI-Tool-Intelligence | Models/tools/framework research |
| Monetization | Packaging, pricing, COGS and revenue experiments |
| Data-Analytics | Metric and event contracts |
| Customer-Ops | Onboarding, support, feedback lifecycle |
| Security-Trust | Security, privacy, permissions, trust |
| .github | Org-wide GitHub defaults |
| browsercrew.github.io | Thin public GitHub Pages/org surface |

## One owner per truth
If two repositories independently maintain the same fact, one is wrong architecturally. The non-owner should link to the owner.

## Product operating chain
Product truth → Workflow → Skill → Agent → Orchestration → Execution → Evaluation → Memory → Improvement.

## Business operating chain
Market evidence → Brand/Positioning → Marketing → Content/Website → Acquisition → Analytics → Customer feedback → Product/Monetization.
