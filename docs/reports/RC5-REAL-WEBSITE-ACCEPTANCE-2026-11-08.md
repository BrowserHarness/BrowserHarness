# Native API Engine RC5 — real-website acceptance, 2026-11-08

**Release decision: NO MERGE.** Four of the eight real-site scenarios passed, two were partial, one was blocked by the absence of an authenticated account in the disposable Chrome profile, and one did not encounter the required real-world drift. This is acceptance evidence for the local `codex/rc5-integration` candidate (base `1d47512`, plus the GraphQL auto-selection correction), not a claim about a released build.

Environment: Windows 11; Chrome for Testing in isolated, disposable profiles; the built BrowserHarness extension and locally running Bridge. Public websites were visited directly. GitHub Actions were not used. No personal sign-in credentials were copied into the profiles. Guest-cart tests used a disposable cart, never checked out, and cleared it after the test.

## Controlled HTTP commerce lab — additional RC5 evidence

On 2026-11-08, `npm run smoke:commerce-lab` passed **26/26 checks** with the built extension, Bridge, and real Chromium against a disposable storefront and separate commerce API, both bound to localhost. The lab uses random, short-lived test accounts, genuine HTTP form login and logout, server-side session cookies, two independent browser profiles, real cross-origin network requests, and an in-memory cart. It requires no external accounts, Docker, database, credentials, or GitHub Actions. All test data and listeners are discarded at exit.

The lab verified that a signed-in account read succeeds at tier 2 without persisting login credentials in the extension's storage, while another profile cannot access that session or its learned Skill. It also verified cross-host product search, a deliberate server endpoint migration causing `API_ENDPOINT_DRIFT`, verified candidate repair followed by explicit promotion, an actual Watch Me cart-write demonstration, and a consent card naming both hosts. Cancel caused no mutation; Approve sent one additional write and the cart was checked and cleared. After logout, the learned account read failed as `API_AUTH`, while the other profile's account still worked. The extension's response to the write remained appropriately cautious (sent, not independently confirmed). In headless Chromium, the test invokes the real Approve button handler through a DOM click because the sticky panel layout interferes with pointer clicking; this does not establish pointer clickability in that viewport.

To reproduce locally: build the extension and Bridge (`npm run build && npm run build:bridge`), point `CHROME` at an installed Chromium executable when needed, then run `npm run smoke:commerce-lab`. The harness and fixture are `scripts/e2e-commerce-lab.mjs` and `scripts/lib/commerce-acceptance-server.mjs`. Existing compatibility checks also passed: API engine **48/48**, API approval **23/23**, typecheck, and Watch Me **26/26** when run independently. A simultaneous Watch Me run initially reported **25/26** due to the sign-in recording starting on a different tab before the test's fallback; an isolated rerun passed with no source changes. This remains a timing concern to monitor.

**Scope:** This is controlled local HTTP integration evidence. It does **not** change the public real-site status table above: 4 PASS, 2 PARTIAL, 1 BLOCKED, 1 NOT TRIGGERED. It is not a Medusa or Saleor deployment or proof of successful authenticated operation on a third-party merchant site. The draft PR remains subject to the real-site release criteria below.

## Follow-up acceptance — 2026-11-09

The November 8 table is the original point-in-time public-site result. On November 9, a separate **public third-party** acceptance run exercised the documented QA customer accounts at `practicesoftwaretesting.com` using two disposable Chromium profiles and the actual Toolshop account API at `api.practicesoftwaretesting.com`. The initial run passed **15/16 checks**. In profile A, website UI login succeeded, BrowserHarness learned and verified the authenticated cross-host `GET /users/me` request, tier-3 execution returned A's identity, and extension storage did not contain the supplied password or the observed live auth token. Website UI logout invalidated the learned account read as `API_AUTH` without returning cached account data. Profile B could not access A's learned Skill; it signed into a different documented demo user and remained signed in when A logged out. No personal credentials, purchases, or checkout were involved.

The sole failed check asserted that a guest visiting `/account` would be redirected away from that URL. That **test assumption was wrong**: a separate read-only inspection of a fresh guest Chromium profile showed the URL remains `/account`, renders **Sign in**, and its `GET /users/me` requests return **401**. The untracked manual acceptance script `scripts/rc5-toolshop-auth-acceptance.mjs` was corrected to assert a 401 response and no 200 response instead; **the revised 16-check script was not rerun**, because the subsequent external-login invocation was rejected by platform safety review. Do not report a 16/16 pass. The script is for explicitly authorized manual public-site QA, never CI.

The authenticated read scenario now has supporting public-site **PASS** evidence. Authenticated profile isolation has strong positive evidence but remains **PARTIAL** until the corrected end-to-end check completes. As of this follow-up, the aggregate public-site assessment is **5 PASS, 2 PARTIAL, 1 NOT TRIGGERED**; the other remaining partial is the *external* cross-host write approval. A guest cart action on Toolshop did not generate a qualifying cross-host API write and cannot close that gate. Natural external endpoint drift still did not occur. The PR remains **DRAFT — NO MERGE**.

Local verification on November 9 used a disposable, correctly versioned Chromium launcher. `npm run smoke:commerce-lab` passed **26/26** again and `npm run gate:api-engine` passed: pinned upstream verification, **151 Bridge tests**, **831 extension tests**, typecheck, builds, MV3 validation, **48/48** API engine checks, **23/23** approval checks, and **26/26** Watch Me checks. These are controlled integration and regression results; they do not substitute for the outstanding public-site gates. GitHub Actions were not used.
